# Virgil

Personal life-tracking dashboard built with FastAPI, SQLite, Jinja2, and HTMX.

Virgil tracks daily habits, training sessions, health metrics, goals, experiments, and personal development programs, all through a mobile-friendly UI in English or Polish with dark/light theme support. Data lives in SQLite (source of truth) with on-demand markdown export for LLM-based reviews.

## Tech Stack

- **Backend**: Python 3.14, FastAPI, aiosqlite
- **Frontend**: Jinja2 templates, HTMX, Alpine.js (CSP build), Chart.js, Lucide icons, all served from `app/static/vendor` (sources and hashes in `SOURCES.json`), with no CDN or Google Fonts request
- **Styling**: Custom CSS with dark/light theme via CSS custom properties
- **Database**: SQLite with WAL mode, versioned migration system
- **Auth**: Multi-user with per-user isolated SQLite databases, email + password + TOTP MFA
- **LLM Integration**: LiteLLM (supports Anthropic, OpenAI, Gemini, Mistral, Groq, Ollama, and more)
- **Charts**: Chart.js (line, bar, sparkline, radar, dual-axis) — theme-aware
- **PWA**: Service worker with offline support, installable on mobile

## Quick Start

### Local Development (uv)

```bash
# Install dependencies
uv sync --locked --extra dev --python 3.14.7

# Run the app (hot reload enabled, port 8123)
uv run python -m app
```

On first launch, navigate to `http://localhost:8123`, sign up at `/signup` (email + password) and complete the onboarding wizard; every account goes through it once. Registration is closed by default, but the **first** account can always be created (bootstrap owner); open it for more users with `VIRGIL_REGISTRATION_OPEN=true`.

`VIRGIL_ENV` defaults to `local` which enables hot reload. Set to `prod` to disable.

### Docker (Local)

```bash
docker compose up -d --build
```

### QNAP NAS Deployment

Virgil runs on QNAP via Docker with Cloudflare Tunnel for zero-port exposure:

```
Browser (virgil.example.com)
    |
    v
Cloudflare Edge
    |
    v  (outbound-only tunnel)
+------------------------------------------+
| QNAP NAS                                |
|  +-------------+    +-----------------+  |
|  | cloudflared  |<-->| virgil          |  |
|  | (tunnel)     |    | FastAPI + SQLite|  |
|  +-------------+    +-----------------+  |
|                          |               |
|                          |               |
|                     /data (DB)           |
|                     (read-write)         |
+------------------------------------------+
```

**Step 1: Create Cloudflare Tunnel**

1. Go to [Cloudflare Zero Trust](https://one.dash.cloudflare.com/) > Networks > Tunnels
2. Create a tunnel, copy the token
3. Add public hostname: subdomain `virgil`, domain `example.com`, service `http://virgil:8123`

**Step 2: Configure secrets**

```bash
cp .env.example .env
# Edit .env — fill in CLOUDFLARE_TUNNEL_TOKEN (required) and API keys (optional)
```

**Step 3: First deploy (one-time)**

Production images are built by GitHub Actions on every push to `main` and pushed
to GHCR (`ghcr.io/krzysztofbury/virgil`). The NAS only needs the compose file,
`.env`, and a `data/` directory — no repo checkout, no building on the NAS:

```bash
ssh <user>@<NAS_IP>
mkdir -p /path/to/virgil/data /path/to/virgil/backups && cd /path/to/virgil
# The container runs as uid 1000; it must be able to write both directories.
chown 1000:1000 data backups
# copy docker-compose.yml + .env here (once — they rarely change)
docker login ghcr.io          # PAT with read:packages — needed if the package is private
docker compose pull
docker compose up -d
```

> **QNAP Container Station**: its compose editor neither substitutes `${VAR}` nor
> reads `.env`. Either run `docker compose` over SSH as above (the containers
> still show up in Container Station), or paste `docker-compose.yml` into the
> editor with every `${...}` replaced by its literal value and recreate the
> application there. If the editor rejects the long-syntax backups mount, use
> the short form `- /path/to/virgil/backups:/backups`, and create the directory
> first: the short form silently creates a missing one owned by root, which the
> container cannot write.

**Deploys after that are automatic**: push to `main` → Actions runs locked checks and audits →
builds and smoke-tests the image (with `GIT_SHA` baked in for PWA cache-busting) → pushes to
GHCR → the `watchtower` container on the NAS notices the new `:latest` within
~5 minutes and recreates `virgil`.

> **Deployment semantics - know what this is**: Watchtower is best-effort
> auto-update, NOT a staged deployment. A broken image is deployed. Two
> signals cover what can then go wrong. A process that stops answering `/livez`
> turns the container unhealthy, and the `autoheal` service restarts it. A start
> that leaves any database unmigrated keeps `/healthz` at 503 and posts one alert
> to `ALERT_WEBHOOK_URL`; it is not restarted, because a restart cannot fix it
> and would cut off every other account each time. Autoheal posts each restart
> to the same URL. With `WATCHTOWER_NOTIFICATION_URL` set, Watchtower also
> reports each deploy, and each poll while an update keeps failing (a registry
> login that expired, for example). A rollback is deliberately not automatic: database migrations are one-way and an older image
> refuses a newer database, so going back means restoring a **pre-migration
> snapshot** from `backups/pre-migration/` (`*-pre-migration-vNNN.db`), as the
> rollback procedure below describes. The CI test gate in front of every image
> remains the first safety net.
>
> **Backups live off the data volume**: compose mounts `VIRGIL_BACKUP_HOST_DIR`
> (default `./backups`) at `/backups`, separate from `./data`, so losing or
> wiping the data directory does not take the copies with it. Point it at
> another disk or share when there is one, with a Linux filesystem: backups are
> published by hard link, which exFAT and FAT do not support. Backups an older setup left in
> `data/backups/` are moved there at the next start. For copies off the machine,
> see [the recovery guide](docs/recovery.md).
>
> **Third-party images are pinned** by version and digest. Watchtower updates
> only `virgil`, so a cloudflared, Watchtower or autoheal upgrade is a reviewed
> edit to `docker-compose.yml` followed by `docker compose up -d`.

**Applying a `docker-compose.yml` change** (Watchtower only replaces the
`virgil` image, never the compose file): copy the new file to the NAS, create
any new host directory it mounts (writable by uid 1000, as above), then run
`docker compose up -d`. With Container Station, carry the same edits into its
editor, keeping your literal values, and recreate the application.

**Force an immediate update:**

```bash
docker compose pull virgil && docker compose up -d virgil
```

**Rollback:** pause Watchtower and pin a known-good `sha-*` image in Compose.
Follow [the rollback procedure](RELEASE.md#rollback), including database recovery
when the failed deployment applied migrations.

## Verification, releases, and recovery

[CONTRIBUTING.md](CONTRIBUTING.md) contains the exact local verification commands.
One CI workflow checks pull requests and main, qualifies the actual production
image, and publishes only after its smoke test succeeds. Version tags alias an
already verified main image and never change `latest`. See [RELEASE.md](RELEASE.md).

The [recovery guide](docs/recovery.md) covers complete offline bundles, integrity
verification, daily encrypted off-site copies to an S3-compatible bucket such as
Cloudflare R2, restore into a new directory, and a restore
drill. Per-user database downloads alone do not include the registry or encryption
key and are not whole-instance recovery artifacts.

The REST API and MCP take a credential in `X-API-Key` or
`Authorization: Bearer`. Each account creates its own **API tokens** under
Settings > Security: a token acts only for that account, with the scopes it was
given (`read`, `write`, `sensitive` for Freedom, `finance`), and can expire or
be revoked at once. The server's `VIRGIL_API_KEY` still works for the one
account named by `VIRGIL_API_USER_EMAIL`. To move off it, create a token with
the same scopes, put it where the key was, then remove both variables.

The MCP wrapper has its own committed dependency lock:

```bash
VIRGIL_API_URL=https://virgil.example.com VIRGIL_API_KEY=your-token \
  uv run --locked --script mcp_server/virgil_mcp.py
```

The app also serves the same tools over Streamable HTTP at `/mcp`, so a client
needs no checkout, `uv` or launcher. It takes the same credential as the REST
API; add the Cloudflare Access service-token headers when the host sits behind
Access:

```bash
claude mcp add --transport http --scope user virgil https://virgil.example.com/mcp \
  --header "Authorization: Bearer your-token" \
  --header "CF-Access-Client-Id: your-id" \
  --header "CF-Access-Client-Secret: your-secret"
```

The endpoint runs in stateless JSON mode; every tool still calls the REST API
(over loopback) with the caller's own credential, so `/mcp` and `/api` share
one auth path, one account mapping and one set of scopes.

Tests and Docker use bundled LiteLLM capability metadata for reproducibility.
Updating that metadata is part of a reviewed dependency update.

## Features

### Dashboard (`/`)

Action first, analytics after. The first block is **Today**: the four A.N.D.Y.
tasks and three routines, each tapped in place through `done > skipped > pending`
without opening Daily, with the count (`n/4`) and `Edit today's log` for
descriptions and notes. With Freedom on, a **Freedom** block marks each tracked
habit clean for today in one tap (a slip opens the habit's day form). Then the
morning briefing (if enabled), **Focus** (the starred goals), the week strip
(energy per day, with a legend) and active experiments, each card with its own
one-tap log for today. Everything that describes the past sits under **Insights** - Oura
vitals with when they last synced, body measurements, the life-score radar and
history - with the year calendar dot-matrix collapsed at the end.

History views share one set of windows: 4, 12 or 26 weeks, picked with `?weeks=`
(12 by default) on Life Scores, Oura's compare chart and daily history, and
Training's Personal Bests. The Daily heatmap stays at 12 weeks, which is what
fits a phone.

There is deliberately no interpretation sentence here: the page states the next
action and the numbers, and leaves the verdict to you.

### Daily Log (`/daily`)
- Energy level (1-10 slider) with `Low / OK / High` anchors
- `n/7 complete today` stated in the card header (three routines plus four A.N.D.Y. tasks), kept in step as you toggle
- Morning/evening routine toggles (three-state: done/skipped/pending) - each shows its state as a word and carries `aria-pressed`
- A.N.D.Y. task system — 4 life areas (Body, Spirit, Self, Relations) with toggle + description; a finished task with a description reads as content, with editing behind `Edit`
- A.N.D.Y. AI generation — uses configured LLM to suggest daily tasks based on goals, training, and weekly context
- Saturday body measurements (weight, arm, waist, hips, thighs)
- Markdown notes with edit/preview toggle
- Per-habit streak counters, the 7-day completion heatmap and a 12-week one, together under `Your trends`. The 12 weeks are a table: each day's count is read out by a screen reader, and each week's average is shown under its column
- Swipe left/right to navigate between days (mobile)
- Arrow keys to navigate between days (desktop)

### Training (`/training`)

One free-text note per session is the only input. Everything else on the page
reads back what was logged:

- Capture form - date, optional duration, and the note itself
- This Week KPIs - sessions count, total volume (Core, kg), total reps
- Correcting history: each set in a day's dialog has `Edit` (movement, set, reps,
  weight, time, equipment, note) and a confirmed delete, so a misread set is fixed
  without SQL and without deleting the whole workout
- Personal Bests - compact per-movement groups with records split by rep count or timed duration, over the shared 4, 12 or 26-week window (12 by default);
  a set on other equipment than the movement's usual one (a dumbbell hang snatch) is its own record
- `Unfinished` - every session whose parse is still waiting, whatever its date
- Year calendar history - duration heatmap with hover and keyboard summaries;
  selecting a training day opens bounded pages of its sessions, sets, notes,
  recovery actions, and delete actions. Navigation keeps every recorded year reachable.

The page previously carried a protocol table, a per-set log form generated from
it, and a rest timer. All three assumed a fixed prescription followed at home;
once training moved to a class that programs the session, the note became the
record and they were removed. The `training_exercises` table stayed — every
logged set references it — but it has no UI and no prescription role.

#### Capture — logging a workout from one note

Write one free-text note from memory after training and let it be parsed:

- **The note is saved before the LLM is called.** Parsing is derived and
  correctable; your own words are the source of truth. A parser failure — no
  provider configured, a timeout, a garbled reply, even a crash — costs you the
  structure, never the record.
- **The parser is confined to a closed movement vocabulary: every non-archived
  row in `exercise_library`** — your whole library, not a CrossFit-only slice
  of it. Movements carry free-form tags (e.g. `kettlebell`, `gym-classic`)
  instead of a single category, and tags organise the picker without gating
  what the parser may recognise: a session's warm-up, stretching, kettlebell
  or barbell work is picked up the same way a CrossFit movement is. A
  movement outside the vocabulary is reported as unrecognised, never
  invented — this is what stops the catalogue filling with `Thruster`,
  `thrusters` and `Thruster 43kg` as three separate exercises. Movement names
  are unique library-wide (migration 019), so there is no same-name-under-
  two-categories ambiguity left to resolve.
- **Nothing is written until you confirm.** The confirmation screen is editable:
  fix a misread weight, skip an entry you did not mean to log, or assign an
  unrecognised movement. The picker groups movements by section, shows their
  tags, puts what you logged recently first and can be filtered by name or tag;
  it stays a native `<select>`, so it works with no JavaScript and can only ever
  submit an exact library name. Refreshing the screen never re-invokes the LLM
  (the parse result is cached in `training_sessions.wod_parsed`), and
  re-submitting a confirmed session cannot double-count it.
- **A rejected field costs you that field, not the form.** An out-of-range value
  re-renders the screen with every other value you typed, the message naming the
  row and the field. Nothing is written and the parse stays armed for the retry.
- **A partial save says so.** If a movement no longer resolves, the rows that do
  are written and `/training` names what was skipped. A blank movement stays
  silent - that is the deliberate skip.
- **One capture per click** (`training_sessions.capture_token`, migration 024). A
  double submit, an F5 or a back-then-resubmit claims the same session and pays
  for one parse. A reused page carrying different text is a new capture, not a
  replay, so the back button cannot drop a note you just wrote.
- **A note that lost its parse can still gain entries.** A session left with only
  its text - a container recreated mid-parse, say - offers `Enter sets by hand`,
  which arms an empty parse and gives you the manual rows.
- **Movements you don't already train** are created with `ad_hoc = 1`: they count
  toward session history, weekly volume and Personal Bests. The flag is what keeps
  the daily-planner context clean of one-off movements.

The vocabulary is yours to curate — add, rename, delete it in
**Settings → App Config**, or over the REST API and MCP (see below). Renaming a
movement that already has logged history is refused, since it would split that
history across two exercises and halve your Personal Bests.

> Weekly volume is not comparable with pre-CrossFit numbers: metcon work counts
> as real Core volume, and a single 21-15-9 thruster couplet at 43 kg is ~1935 kg.
> That is intentional — see CHANGELOG.

### Freedom (`/freedom`)
Habits you are breaking free from. Hidden by default: enable **Freedom** in
Settings > General > Modules and tick the habits to track - porn, alcohol,
nicotine, cannabis, drugs, gambling, social media, sugar, or one in your own
words. Unticking a habit stops tracking it and keeps its history. The old
`/feniks` address redirects here.

- **Today** - every tracked habit with its streak and this week's clean rate,
  checked off as *Clean* or *Slipped* in one tap
- **One habit at a time** below it: its why, the bricks hero (urges survived)
  with a Monday-to-Sunday week strip, the day log, brick capture and the timeline
- **Each habit defines its own slip** - the button label (*I watched*, *I drank*),
  an optional amount with a unit and threshold, an optional near miss, and a
  written definition shown above the day question. Porn keeps the old measurement
  contract: watched means at least five total minutes of intentional viewing,
  shorter exposure stays clean and belongs in the note, and the near miss is
  edging. Everything is editable under the habit's settings
- **Bricks** - one distinct decision episode resolved before a slip; each carries
  a required memory hook, craving (0-10) and a short story (Gola's brick method),
  and can be edited or removed with confirmation
- **Day log** - marking a slip records that habit's relapse event once; correcting
  the day back to clean removes only that marker and clears slip-only fields
- **Weekly clean rate** - a slip lowers the week's rate (target 75%) and never
  resets it to zero
- **Timeline** - days and their bricks together, newest first. A day's date opens
  it in the day form, which can also delete a logged day
- **Relapse records** - what the streak is counted from, listed per habit. A
  record a slipped day wrote is corrected through that day; any other (older or
  imported) edits its date, type and note, or is deleted after a confirmation

Migration 034 moves No Porn history - days, bricks, relapse events, start date,
target and why - onto a Porn habit.

### Oura (`/oura`)
Daily and monthly Oura Ring metrics — sleep, readiness, activity, HRV, stress, and more.

- **API Integration**: OAuth2 connection to Oura Cloud for automatic data sync
- **Webhook Support**: Real-time data push from Oura with HMAC-SHA256 signature verification
- **Readiness vs baseline**: the page opens on today's readiness against the mean of the previous 7 days, the signed delta and one word (`above`, `steady`, `below`, at a 3-point tolerance). A rule over stored numbers - no generated advice and no LLM call
- **Today's Vitals**: grouped into Sleep, Activity and Recovery - sleep score, activity, steps, readiness, HRV, RHR, stress/recovery minutes. Activity and steps fall back to yesterday's values (with label) when today's data isn't yet available from the API
- **Compare metrics**: the dual-axis chart (HRV/RHR + sleep/readiness scores) over the shared 4, 12 or 26-week window, last on the page because it answers a different question from the default trend
- **Daily History**: Browsable table over the same window
- **Freshness**: the page says when Oura data last synced, in amber once that is over a day ago
- **Monthly Trends**: Aggregated averages with Chart.js trend charts
- **Manual Entry**: Fallback form for entering monthly averages
- **Rate Limit Handling**: 429 responses trigger exponential backoff with Retry-After

### Bloodwork (`/bloodwork`)
Blood test results organized by marker category with reference ranges, flag indicators, and per-marker trend charts.

On a phone each marker is one row - latest value, H/L status and the signed
change from the result before it - with the full date matrix under `All results`.
A marker's chart view lists its results under `Correct ... results`: each one's
date, value, text and flag can be fixed, or the result deleted, without SQL. The
flag is recomputed from the reference range unless a lab flag is chosen.
A wide screen gets the matrix directly. One Jinja macro renders both, so the two
views cannot drift apart.

### Life Scores (`/life-scores`)
Periodic self-assessment across 8 life areas with power level composite score and radar chart visualization. On the dashboard, `Over time` charts the power level across the shared 4, 12 or 26-week window (each area one legend tap away), and `History` lists every assessment in it, complete or not.

### Goals (`/goals`)
Canonical goals and one-off execution reps across 8 life areas with 1yr/3yr/10yr horizons.

- **Current focus** - star a goal from any area or any horizon to bring it here.
  The limit is advisory: above three the page says so and still saves the fourth,
  because a cap that refuses a write is worse than a crowded list
- **One horizon at a time** behind a switch, instead of all three at once
- Areas with nothing in the selected horizon render as one compact line each
- **One `Add goal` flow** that asks for the area and the horizon, replacing the
  24 always-open inputs the empty state used to render
- Goal status and start/end windows make active, paused, completed, and abandoned
  outcomes explicit
- **Execution reps** carry a day/week/month/quarter/year period, due date, and
  pending/completed/carried/skipped state. Carrying preserves the old record and
  creates the next pending rep. Calendar weeks always run Monday through Sunday
- Repeated metrics remain experiments, which can optionally link back to a goal;
  one-off calendar commitments remain reps rather than fake experiment counters
- REST and MCP 2.x provide bounded goal/rep reads plus idempotent create, update,
  delete, complete, carry, and skip writes
- **Undo a delete**: a deleted goal (one without reps, as before) waits under

### Finance (`/finance`)
A household's financial resilience, without a bank integration. The user
defines a **fortress**: named layers (seeded as Cash cushion, Protection,
Independent income and Investments, all renamable), accounts in them, and
balances recorded once a month.

- Amounts are stored exactly, in minor units of one base currency (default
  PLN); an account in another currency may also keep its native amount
- A balance holds until the account's next one, so a month where one account
  was not updated still has a total and lists that account as stale
- Accounts can be `own`, `joint` or `excluded` (shown, never counted)
- Virgil computes the cushion (layers that count toward it), how many months of
  essential cost it covers (the cost that applied that month), the share of that
  cost covered by income independent of work and by all stable income, and a
  score from editable per-layer rules. Seeded rules: cushion 12/6/3/1 months for
  40/30/20/10 points, policies 35 (life 10, health 8, property 7, vehicle 5,
  income loss 5; not applicable leaves the total), independent income
  50/30/20/10% for 25/20/15/10. The score is given twice: with income independent
  of work only, and with all stable income. A missing input makes the score
  unknown, not zero
- The page (on under Settings > Modules) shows the cushion, its months, the
  score and the share covered by independent income, the cushion over time,
  each layer with its accounts, policies or income, and a "Record balances"
  form that starts at the latest balances. `/finance/setup` edits the layers
  and their rules (thresholds written as `12:40, 6:30`), accounts, essential
  cost, income and insurance
- MCP/REST, all behind the `finance` scope (`VIRGIL_API_FINANCE=true` for the server key):
  - `get_finance_overview` / `get_finance_history` → `GET /api/finance`,
    `GET /api/finance/history`
  - `record_balances` → `PUT /api/finance/balances/{date}`: a whole snapshot in
    one call, all or none; an unknown account refuses it
  - `upsert_finance_account` → `PUT /api/finance/accounts`
  - `set_finance_assumptions` → `GET/PUT /api/finance/assumptions`: essential
    monthly cost from a date, income sources, insurance policies, base currency
  - `get_finance_scoring` / `set_finance_scoring` → `GET/PUT
    /api/finance/scoring`: the layers and their score rules

Add your own entries, edit/delete them; built-in entries can be archived (hidden from the parser) but never edited or deleted. ## Background work

No request waits on an LLM or on Oura. Backups, exports, Oura syncs and every
paid AI call are **durable jobs**: the route (or the scheduler) writes what you
asked for and returns; a bounded worker does the rest and survives a restart.

**Enqueueing starts the work immediately.** A job you asked for does not wait
for the next scheduler tick: the route wakes a bounded worker pass, so the click
is answered in milliseconds and the job is running a moment later. The 60-second
tick stays as the safety net for scheduled work and for anything a restart left
behind. Set `VIRGIL_WORKER_WAKE=false` to fall back to tick-only pickup.

**Paid AI work is treated differently from operational work.** Backups and syncs
retry themselves; a paid call does not. A timeout or an API error does not prove
the provider refused the request, so a second attempt could buy the same answer
twice. Those kinds get one attempt, an explicit manual retry, and a warning on
the card when the outcome is genuinely uncertain. A publication ledger records
what already reached you and outlives job pruning, so even a crash between the
write and job completion cannot cause a double charge.

| Kind | Retry | Triggered by |
|---|---|---|
| `backup`, `oura_sync` | automatic, bounded | manual button, schedule, Oura webhook |
| `morning_briefing` | manual | dashboard button, daily schedule |
| `wod_parse` | manual | saving a training note |
| `andy_generation` | manual | the AI button on Daily |
| `experiment_summary` | manual | the scheduler, one missing week at a time; or the per-week button |
| `onboarding_enrichment` | manual, per step | confirming onboarding |
| `medical_import` | manual | uploading a blood panel in onboarding |

Progress appears in the **notification tray** (top right). The tray polls
`/api/jobs/active`, so anything still queued or running is visible on every
page, not only where you started it, together with the outcome of whatever the
current page enqueued. Confirmations fade after a few seconds; errors and
unfinished jobs stay until you deal with them. Settings > Automation keeps the
full recent-job history with the same retry controls.

## Security

### Authentication
- Email + password with bcrypt hashing
- Optional TOTP MFA via `pyotp` + `qrcode`. The setup QR is generated for the signed-in user at `/mfa/qr.png`; the secret is not put in a URL, and responses that carry it are `Cache-Control: no-store`
- Signed cookie sessions via `itsdangerous.TimestampSigner` (7-day expiry)
- MFA-pending sessions blocked from protected routes; they expire after 10 minutes, and `/login` treats them as signed out
- A signed session whose account was deleted or disabled is cleared on the way to
  `/login`, instead of looping between `/` and `/login`

### Middleware Stack
Request processing order:
1. **Security Headers** - CSP with scripts only from `'self'` or inline with a per-response nonce (no `'unsafe-inline'` or `'unsafe-eval'` for scripts, no inline event handlers), X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy
2. **Rate Limiting** — 120 req/min general, 10 req/min for auth endpoints (per-IP sliding window)
3. **Authentication** — Cookie-based session verification (public paths: login, signup, MFA, offline, healthz, service worker, per-user Oura webhooks)
4. **Feature Flags** — Loads `feature_*` settings from `app_settings` into `request.state.features` for templates and route guards
5. **CSRF Protection** — Double-submit cookie on all POST forms (exempt: Oura webhook endpoint)

### Data Protection
- OAuth tokens and client secrets: Fernet-encrypted in database
- LLM API keys: Fernet-encrypted at rest
- Webhook secrets: stored in database, used for HMAC-SHA256 signature verification
- Encryption key: `VIRGIL_ENCRYPTION_KEY` env var, or auto-generated at `data/virgil.key` (0600 permissions)
- Server-side input validation on all form endpoints

## Data Model

- `training_exercises` — the row every logged set references; seeded, no longer a UI-managed protocol
- `training_sessions` + `training_entries` — workout logs
- `habits` - Freedom habits: slip label and definition, amount unit and threshold, near-miss label, start date, target, why, tracked flag

- `feniks_journal`, `feniks_pleasures` - the No Porn program's journal and pleasures, read by `/api/noporn` and the markdown download
- `oura_daily` — Oura Ring per-day data (from API or webhook)
- `oura_monthly` — Oura Ring monthly averages (computed from daily or manual)

- `life_scores` — periodic assessments

### Three-State Toggles
Habit and task items use a three-state cycle: `done` > `skipped` > `pending`, mapped to `[x]` / `[-]` / `[ ]` in markdown. On the dashboard each tap advances one item (`POST /daily/{date}/cycle`) and leaves the rest of the day as it was.

## Oura Ring Integration

Virgil connects to the Oura API v2 via OAuth2 for automatic daily health data sync, with optional webhook for real-time updates.

### Setup
1. Register an app at [cloud.ouraring.com/oauth/applications](https://cloud.ouraring.com/oauth/applications)
2. Set the redirect URI to `{VIRGIL_BASE_URL}/settings/oura/callback`
3. In Virgil Settings > Integrations, enter your `client_id` and `client_secret`
4. Click "Connect to Oura" and authorize access
5. Click "Sync Now" to pull the last 30 days of data

### Webhook (Real-time Sync)
1. In Settings > Integrations, click "Enable Webhook" on the Oura card
2. Virgil registers one subscription per handled `(event_type, data_type)` pair with the Oura API, using a **per-user callback URL** (`/api/oura/webhook/{id}`) that routes events to the right user's database
3. Oura sends a verification challenge — Virgil responds to complete registration
4. Subsequent data events trigger a 2-day sync window with HMAC-SHA256 signature verification against the user's encrypted webhook secret
5. The scheduler reconciles remote state, renews each subscription before expiry and retries degraded or interrupted work
6. To remove, click "Disable Webhook" - Virgil confirms remote teardown before credentials or user data can be replaced

Subscription orchestration is provider-neutral. The coordinator owns desired
state, bounded retries, leases and atomic publication; the Oura adapter owns
discovery, callback matching, renewal and teardown semantics. Settings reports
pending, active, partial, retrying and disabling states instead of treating a
partially registered webhook as fully active.

**Note**: Your `VIRGIL_BASE_URL` must be publicly reachable for Oura to deliver webhook events.

**Cloudflare Access**: if the site sits behind Access, add a **Bypass policy for the path `/api/oura/webhook/*`** — Oura's verification challenge (GET) and event deliveries (POST) are unauthenticated server-to-server calls and get bounced to the Access login page otherwise. The endpoint authenticates on its own: opaque per-user callback ids plus HMAC-SHA256 signatures.

Supported data types: `daily_sleep`, `daily_readiness`, `daily_activity`, `daily_stress`, `sleep`, `workout` (event types `create` + `update`).

### What Gets Synced
Daily data is stored in `oura_daily` (per-day) and aggregated into `oura_monthly` (averages):
- Sleep score, readiness score, activity score
- Steps, sleep duration, deep sleep, REM sleep
- Resting HR, lowest HR, HRV
- Stress (high) and Recovery (rest) — displayed in minutes
